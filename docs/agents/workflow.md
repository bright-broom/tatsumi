# 自律作業のワークフロー

エージェントが人に聞かずに進めてよい範囲と、止まるべき範囲を定める。

## 基本ループ

1. **現状把握**: `git status`、`CLAUDE.md`、関連ファイルを読む。推測で書かない。
2. **最小の変更を選ぶ**: 目的に必要な差分だけ。ついでの整形・リネーム・依存追加をしない。
3. **実装**。
4. **検証**: `npm run verify`。動作に関わる変更は `npm run build && npm run smoke`。UI は実際に表示して確認する。
5. **自分の diff を敵対的に読む**: 何が壊れうるか（セクション ID とナビ、型、画像パス、`sub` ページのリンク）。
6. **ブランチ → コミット → push → ドラフト PR**。

## 自分で決めてよい

- 文言の誤字修正、alt の改善、お知らせの追加（情報源が与えられている場合）
- バグ修正、型の改善、アクセシビリティ修正（見た目を変えない範囲）
- ドキュメント更新、`scripts/` の改善
- 既存パターンに沿ったコンポーネントの追加・変更

## 先に人間へ確認する

| 内容 | 理由 |
|---|---|
| 新しい依存パッケージ、テスト基盤の導入、CSS 方針の変更、ESLint ルールの緩和 | 保守コストが発生する |
| TODO の値（予約 URL・SNS・会社概要） | 事実情報。推測は誤情報になる |
| 画像の追加・差し替え | 権利確認が必要 |
| `site.url`、環境変数、送信元ドメイン、Vercel 設定 | 本番に直結 |
| 料金・営業時間・所在地など事実情報の変更 | 出典が必要 |
| 履歴の書き換え（rebase/force push）、`main` への直接 push | 不可逆 |
| 問い合わせ API の仕様変更（必須項目、送信先） | 運用に影響 |

## 失敗時の扱い

- `verify` が落ちたら、原因を特定してから直す。テストやチェックを外して通さない。
- `npm run build` がフォント取得で落ちる場合はネットワーク要因。コード変更で回避せず、環境の問題として報告する。
- ビルド警告は 0 件が基準。出たら直す。

## 次の一手の候補（優先度順）

エージェントが自律的に選ぶときの目安。実施前に人間へ確認が必要なものは ★。

1. CI（`.github/workflows/ci.yml`）の green を維持する。
2. （完了）ESLint 導入済み。
3. ★ Turnstile を本番で有効化する（コードは実装済み・既定は無効）。キー発行、Vercel への環境変数設定、`/privacy` への記載が必要（`architecture.md` 参照）。
4. ★ レート制限を共有ストア（Upstash / Vercel KV）に移す。
5. a11y 確認（フォーカス表示、Lightbox のキー操作、見出し階層）。
6. （完了）画像は `next/image` に移行済み。
7. ★ TODO 項目の確定（クライアントからの情報待ち）。favicon 用のシンボルマークもここに含む（`architecture.md` 参照）。
8. ★ CSP の導入（Turnstile の本番有効化後、レポートのみ → 強制の順で）。
